# 26. guest-write.spec.ts flake: the real fix, and why the first two weren't it

## Status

Accepted. Supersedes ADR 0025's Decision — its diagnosis groundwork (the trace-level `net::ERR_ABORTED` finding, the CDP evidence-gathering method) was real and stays useful, but the fix it shipped did not work, and this ADR explains why with direct evidence rather than another guess.

## Context

ADR 0025 shipped an "await generation kickoff before navigating" fix based on two failing CI traces both showing `/api/generate` completing server-side (`status: 200`) but `net::ERR_ABORTED` client-side. The next three CI runs on the same PR: fail, pass, fail — the fix commit itself failed, and a docs-only commit afterward (touching nothing behaviorally) failed identically. Since a docs-only commit cannot regress anything, this proved the fix hadn't actually closed anything; it just hadn't been given a large enough sample to show it yet.

Further trace inspection (this same failing run) showed *why* the ordering fix couldn't have worked: the `/api/generate` fetch takes ~365ms end to end, while the client-side navigation to `/story` (the RSC payload fetch) completes in ~30-50ms. Awaiting kickoff before navigating only delays the navigation by one microtask — nowhere near enough separation for the fetch to be clear of the navigation before it lands. The same trace also showed Next's own automatic prefetch requests for `/login` and `/signup` (rendered as header links, prefetched into the viewport per Next's `<Link>` behavior) aborting at the same moment as `/api/generate` — suggesting some navigation-triggered cancellation or connection-contention mechanism broader than just this one app fetch.

A second fix was built on that broader theory: defer calling `generateNext`/`submitAndContinue` until `/story`'s own mount effect, via a `pendingKickoff` flag queued from the home page before navigating — so the fetch would never be issued from a page that's mid-navigation-away at all. Before shipping it, this ADR's own investigation found something ADR 0020 and 0021 had both stated as established fact: **this flake had never once reproduced locally.** That turned out to be about sample size, not environment — `npx playwright test --repeat-each=20 e2e/specs/guest-write.spec.ts` reproduced it locally at roughly the same rate CI was showing (4/60, then 8/120 on a second run), using nothing but the existing harness on a dev machine. A single run, or even ADR 0020's own `--repeat-each=10` soak, was just below the sample size needed to catch it reliably.

That local repro loop is what actually settled this. Tested directly against the second (deferred-kickoff) fix: **the failure rate didn't change** (8/120, same order as before). So that fix wasn't it either — the connection-contention/navigation-cancellation theory, however plausible from the trace evidence, wasn't the actual mechanism, or wasn't a sufficient one on its own.

With a working repro loop in hand, the question became answerable directly instead of by further inference: temporary `console.log` instrumentation in `onChunk`/`onDone`/`onError` (StoryContext.tsx's `runGeneration`) was added and run against the loop until it caught a live failure. The console log, captured in the trace: `onChunk` fired twice (34 chars, then 65 chars — exactly the two mock chunks) and `onDone` fired cleanly. **`onError` never fired.** The application never observed a failure. The paragraph completed and committed correctly every single time this was checked, including on runs Playwright's own assertion reported as failed.

That is the actual finding: `net::ERR_ABORTED` in the Chromium DevTools Protocol network trace does not correspond to anything the page's own `fetch()`/`ReadableStream` reader ever sees as an error. It's a CDP-level artifact below the application layer — real, and still likely tied to Next's navigation-triggered request handling given the correlated timing with the `/login`/`/signup` prefetch aborts, but not something the app's own code path is ever exposed to. Both prior fixes were solving a problem the application doesn't actually have.

What the application *does* have: `guest-write.spec.ts`'s first test asserts on an intermediate, partial-text state of the streaming preview (`toContainText("The lighthouse had not blinked")`, before the second chunk lands). That state depends on React actually painting between the two `onChunk` dispatches, which are only `delayMs: 80` apart. Under real CPU contention — GitHub's shared runners, or a dev machine running the same test 100+ times in a tight loop — the two dispatches (and the following `onDone`) can get processed by the main thread closely enough together that no separately-observable intermediate paint occurs; the DOM goes straight from empty to fully committed. 80ms was never given real margin against that; it was tuned for a fast, idle machine.

## Decision

**Revert both structural changes from the first two attempts.** `generateNext`/`submitAndContinue`/`switchProviderAndRetry` go back to their original synchronous, non-`Promise`-returning form, and `src/app/page.tsx`'s `handleStart` goes back to calling them directly before `router.push`. The `pendingKickoff`/`queueKickoff` mechanism (the state field, the two reducer actions, `/story`'s mount effect) is removed entirely. Both were verified — not assumed — to have no effect on the actual failure rate, using the repro loop above. Keeping either now would be exactly the "unverified change defended as shouldn't hurt" pattern ADR 0020 was written to stop: extra surface area with proven-zero benefit.

**Keep two changes that survive on their own merits, independent of this flake:**

1. `streamGeneration.ts` now distinguishes an intentional abort (`signal.aborted` — this call's own `AbortController`, set only by `StoryContext`'s `abortRef.current.abort()`) from any other exception merely named `AbortError`. The old code treated every `AbortError` as intentional and returned silently. That's a real latent bug independent of this flake's actual cause: *if* a genuine unrequested cancellation ever throws that shape, it now correctly surfaces as `kind: "stream-aborted"`, which `StoryContext`'s existing silent-retry-once logic already knows how to recover from. `streamGeneration.test.ts` gained a case for exactly that scenario, and its two existing "stays silent" cases now actually abort the passed-in signal (they didn't before — they threw an `AbortError`-shaped exception without ever touching the real signal, which is why they kept passing throughout this investigation despite the code they were meant to guard having a real gap in it).
2. `guest-write.spec.ts`'s `delayMs` for this test's mock stream raised from `80` to `400` — real margin for the intermediate-paint assertion to survive scheduling jitter, rather than a value that only ever worked on a fast, idle machine.

**Verification:** the local repro loop that caught this (`--repeat-each=20` through `--repeat-each=60`, several runs) went from a consistent ~7% failure rate (4/60, 8/120, matching CI's own recent history) to 330/330 clean after the `delayMs` change — the same loop, unmodified, now finding nothing. That's the standard this repo already holds itself to (ADR 0020): a fix is confirmed by the repro that caught the failure no longer catching it, not by a single clean run.

## Consequences

This test's real nature was a UI-paint-timing assertion wearing a networking-flake costume — worth remembering if any other spec asserting on an intermediate streaming state (`turn-policy.spec.ts`, `security-headers.spec.ts`'s mid-generation walk) ever shows the same symptom: the fix is likely the same (real margin on the mock's `delayMs`), not another timeout bump.

The bigger process note: ADR 0020 and 0021 both stated, as settled fact, that this flake never reproduces locally. That was true at `--repeat-each=10` and below; it stopped being true at `--repeat-each=20`+. The next time a CI-only flake resists diagnosis, try a larger local repeat count *before* concluding local reproduction is impossible — it's a much faster loop than round-tripping through CI, and it's what actually made this investigation converge instead of guessing a third time.

The CDP-level `net::ERR_ABORTED` itself remains formally unexplained — plausible but unconfirmed as some interaction with Next's navigation-triggered request handling (the correlated `/login`/`/signup` prefetch aborts). Since it's now demonstrated to never reach the application as an observable failure, closing that gap isn't necessary for this ADR's purpose, but it's worth knowing about if a *future* symptom looks like an actual app-visible failure racing navigation — the CDP trace alone isn't sufficient evidence of that; check `onChunk`/`onDone`/`onError` directly, the way this investigation eventually did.

## Rejected

- **Awaiting kickoff before navigating (ADR 0025's fix).** Reasoned from real trace evidence, but the actual timing gap it closed (one microtask) was negligible next to the ~300ms+ fetch it was racing. Falsified by CI itself: the fix commit failed, and a docs-only commit after it failed identically.
- **Deferring kickoff to `/story`'s mount effect.** A reasonable-looking response to the correlated prefetch-abort evidence, but directly falsified by the local repro loop (8/120 failures with the fix in place, same order as without it) before it was ever pushed to CI a second time.

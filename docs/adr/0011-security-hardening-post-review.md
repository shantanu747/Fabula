# 11. Security hardening after the v2 review

## Status

Accepted.

## Context

The accounts, persistence, and sharing work recorded in `docs/adr/0009-accounts-and-persistence-architecture.md` and `docs/adr/0010-shared-story-feed-and-safety.md` was reviewed for security before being committed. The review found one externally exploitable vulnerability and a set of server-side input-trust gaps. This record covers the fixes, because two of them encode tradeoffs and one encodes a non-obvious platform detail that a future reader would otherwise be likely to undo.

ADR 0009's "defense in depth" section already established the posture that the proxy layer is never the sole authorization boundary, and that every route handler touching story data independently re-checks `auth()` and re-verifies row ownership. That covers *who* is calling. It did not cover *what they send* or *where the app navigates afterward*. This record extends the same posture along those two axes; it does not supersede 0009 or 0010, and nothing in either becomes false.

One framing correction worth preserving, because it changed the shape of the fix: the redirect flaw was initially described as an XSS. It is not. Next.js 16.3.0 explicitly blocks `javascript:` URLs in `completeHardNavigation` (`node_modules/next/dist/client/components/segment-cache/navigation.js`), so an attacker-controlled navigation target cannot execute script. It can only send a *just-authenticated* Writer to a foreign origin — a credential-phishing vector rather than code execution, since the victim signs in on the real domain with valid TLS and is bounced to a lookalike only after success.

## Decision

**Redirect targets are validated by origin resolution, not string matching** (`src/lib/auth/callbackUrl.ts`). The `callbackUrl` query parameter was being read straight from the URL and handed to `router.push()` after a successful credentials sign-in on `/login` and `/signup`. The obvious fix — accept only values matching `startsWith("/") && !startsWith("//")` — is wrong, and this is the part worth recording: browsers normalize backslashes to forward slashes in special schemes, so `/\evil.example` passes that check and still resolves to `https://evil.example`. Next's router builds its navigation target with `new URL(addBasePath(href), location.href)` in `dispatchNavigateAction`, so the only safe rule is to reject anything that resolver would treat as external. `safeCallbackUrl` therefore resolves the untrusted value against the real origin, compares origins, and returns `/` on any mismatch — which also catches `javascript:` inputs, since those resolve to origin `"null"`. This was verified empirically against every vector rather than reasoned about: the backslash bypass was missed on the review's first pass and only caught by testing, which is precisely why a prose note here is worth more than a code comment alone.

Two supporting choices: `origin` is a parameter rather than a `window.location.origin` read inside the function, so the module stays SSR-safe and directly testable, and call sites invoke it from client event handlers rather than during render, where `window` does not exist. Delegating instead to Auth.js by switching to `signIn("credentials", { redirect: true, callbackUrl })` — whose default `redirect` callback does neutralize foreign origins — was rejected: it would discard the inline "Incorrect email or password." error handling that `redirect: false` exists to support. The Google button already had that Auth.js protection and was not vulnerable, but it now receives the sanitized value too, so exactly one validated value flows to every navigation on those pages. `src/proxy.ts` needed no change: it only ever writes `req.nextUrl.pathname`. The producer was never the problem; the consumer was.

**Registration responses are deliberately uninformative** (`src/app/api/auth/register/route.ts`). The endpoint previously returned a distinguishable `409` for an already-registered address, which let anyone probe whether an email had a Fabula account. It now returns an identical `201 { ok: true }` either way. The password is hashed *before* the existence branch so that bcrypt's cost — the dominant term in the handler's latency — is paid on both paths and timing does not restore the oracle. The implementation uses `onConflictDoNothing({ target: users.email })` rather than select-then-insert, mirroring the pattern already used for duplicate reports in `api/stories/[id]/report`: it is atomic against a concurrent signup for the same address, it cannot clobber an existing account's password, and it removes a pre-existing race where two simultaneous registrations would hit the unique constraint and produce a 500. A silent no-op is safe here because the client's follow-up `signIn()` is what actually decides whether the caller receives a session.

**Request bodies are bounded server-side, sharing the UI's constraints** (`src/lib/story/validation.ts`). `targetLength` was constrained to 6–30 by the slider but accepted as any `number` by `POST`/`PATCH /api/stories`; `/api/generate` checked only `Array.isArray(storySoFar)` and never validated the scene-setting hints at all, despite writing paragraph elements straight into `story_paragraph` and the provider prompt. The shared guards now check paragraph element shape, bound `targetLength` to an integer within the UI's range, and cap the free-text hints. This required moving `MIN`/`MAX_TARGET_LENGTH` out of `StoryContext.tsx` into `src/lib/story/constants.ts`: under RSC, a `"use client"` module's exports become client references when imported from a server module, so a route handler importing those constants from the context would have received a proxy object rather than the numbers — a silent failure, not a build error. The constants are re-exported from `StoryContext` so existing client call sites are unchanged.

## Consequences

- Signup's duplicate-email feedback is now vague by design — a Writer who already has an account and mistypes their password sees "We couldn't sign you in. If you already have an account, try signing in instead." rather than a definite "that email is taken." This is the accepted cost of closing the enumeration oracle, not a UX oversight; making it specific again reopens the leak.
- `src/lib/story/validation.ts` is now the shared server-side trust boundary, and the `isValidBody` functions in `api/generate` and `api/stories` read as compositions of it. New route handlers that accept story data should extend it rather than growing per-route type guards, or the bounds will drift apart again.
- Likewise, `safeCallbackUrl` is the only sanctioned way to consume a `callbackUrl`. Nothing enforces that mechanically — there is no lint rule — so it is a convention that depends on this record being read.
- Client and server now enforce the same numeric bounds from one `constants.ts`, so drift is limited to whoever edits that file. The hint length caps (500 characters for theme and characters, 2000 for opening lines) are an engineering judgment made during this pass, not a product constraint the Writer specified — they are generous enough not to affect real use, but they are the arbitrary part of this change and the right thing to revisit if longer input is ever wanted.
- Enumeration is closed on the response and timing channels of the registration endpoint specifically. It is not a general guarantee: there is still no rate limiting anywhere in the app, consistent with the posture `docs/adr/0010` and `docs/PRD.md`'s v1 key risks already accepted, so an attacker with unlimited attempts retains other avenues that were not measured. Rate limiting remains the honest next step if any of these surfaces sees real abuse.
- The review found no injection, XSS, or authorization bypass in the v2 work, and that negative result is worth recording so the next reviewer knows what was already covered: Drizzle parameterizes every query including the feed's `offset`, React escapes all rendered story and author text with no `dangerouslySetInnerHTML` anywhere, and every story-touching route re-checks ownership as 0009 describes. The JWT session-revocation limitation noted in 0009 is unchanged by this pass.
- 0009's closing note that migration tooling was never exercised because no `DATABASE_URL` was available is now partly stale: live queries were run against a real Neon database while verifying these fixes. `drizzle-kit generate`/`migrate` itself still has not been run end to end, so the substance of that note stands.

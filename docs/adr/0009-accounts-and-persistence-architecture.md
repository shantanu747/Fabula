# 9. Accounts and persistence architecture

## Status

Accepted.

## Context

`docs/PRD.md` §3 named accounts, a persisted story library, and sharing as the confirmed v2 direction, and the Writer asked for it directly: auth, persistent sessions, stories per user, and a foundation for sharing. Before this, Fabula had no database and no auth (`docs/adr/0007-client-state-architecture.md`) — introducing both is exactly the kind of new-dependency decision `AGENTS.md`'s stack constraints call out as needing deliberate justification, not default reach.

Product-level questions (hosting/DB choice, auth methods, guest access, sharing shape, feed safety) were resolved directly with the Writer beforehand and aren't re-litigated here. What's left, and what this record covers, are the engineering decisions made to implement that direction: ORM, auth library and session strategy, password handling, and — the least obvious part — how server persistence coexists with the client-authoritative state model ADR 0007 already established, without undoing it.

## Decision

**Database & ORM**: managed Neon Postgres, accessed via `drizzle-orm`'s Neon HTTP driver (`src/lib/db/client.ts`). Drizzle over Prisma: no codegen daemon, a schema that's plain TypeScript, and a natural fit for Neon's HTTP driver in Vercel's serverless functions (no persistent connection pool to manage). The client is constructed lazily behind `getDb()`, exactly mirroring the lazy-init pattern `src/lib/providers/anthropic.ts` already uses for its SDK client — so a missing `DATABASE_URL` fails at first *use*, not at module load, and doesn't break `next build`/`next dev` for anyone who hasn't provisioned a database yet.

**Auth**: Auth.js v5 (`next-auth@beta`) with `@auth/drizzle-adapter`, a `Credentials` provider (email/password, hashed with `bcryptjs` — pure JS, no native binary, safe in serverless runtimes) and a `Google` provider. **Session strategy is JWT, not database sessions**, despite having a database and despite the adapter defaulting expectations toward DB sessions: Auth.js's adapter only persists a row to the `sessions` table for adapter-linked (OAuth) sign-ins — a `Credentials` provider's successful `authorize()` never gets a DB session written for it. Configuring `session: { strategy: "database" }` here would silently break email/password login (a session that never persists) while Google sign-in kept working, which is a much worse failure mode than picking JWT sessions up front. The adapter still handles `users`/`accounts` persistence under JWT sessions — only the session storage mechanism differs. This corrects an assumption in the original implementation plan, which had proposed database sessions without accounting for this Credentials-provider gap; the discrepancy was caught during implementation, not before.

**Schema** (`src/lib/db/schema.ts`): `users`/`accounts`/`sessions`/`verificationTokens` follow `@auth/drizzle-adapter`'s required Postgres shape exactly (column names and types matter — the adapter's own type definitions were read directly, not assumed), extended with a nullable `passwordHash` on `users` for Credentials sign-ins (null for Google-only accounts). App-specific tables — `stories`, `storyParagraphs`, `storyReports` — are a deliberate structural mirror of the client-side `StoryState`/`StoryParagraph` shapes in `src/lib/story/types.ts`, not an independently-designed model, so the two stay easy to reason about together.

**Persistence model — write-through mirror, client stays source of truth**: this is the core decision that keeps ADR 0007 intact rather than superseding it. While a story is actively being written, `StoryContext` (client) remains authoritative, exactly as before — nothing about guest use or the moment-to-moment write flow changes. For a signed-in Writer, `ensureStoryId()` lazily creates a `stories` row via `POST /api/stories` on that Writer's *first* turn (not at story-start time, so a signed-in Writer who never writes anything never gets an empty row), and every subsequent `/api/generate` call carries the resulting `storyId`. The route handler persists any paragraphs in the submitted `storySoFar` that aren't yet in the database — computed as a diff against the database's actual stored paragraph count, not a client-asserted "here's what's new" field, so a client bug or a retried request can't cause double-writes or dropped paragraphs — before generating, and persists the AI's paragraph once its stream completes. This adds no new per-turn network request: persistence rides along on the `/api/generate` call that already happens every turn.

**Guest-story adoption is implicit, not a separate flow**: the original plan sketched a dedicated "adopt this story" prompt/endpoint for a Writer who signs in mid-story. That wasn't built. Because persistence is diff-based against the full `storySoFar` array rather than "just the latest paragraph," a guest's entire pre-login paragraph backlog gets persisted in one shot the moment `ensureStoryId()` fires on their first post-login turn — the general mechanism already produces the adoption behavior for free. This is a scope reduction made as an implementation-detail engineering call, not a product-scope change: the Writer-visible outcome (a pre-login story isn't lost) is the same as what a dedicated adoption flow would have delivered, with less code and one fewer UI surface to maintain.

**Defense in depth**: `src/proxy.ts` (Next.js 16's `middleware` file convention, renamed per its own deprecation notice) redirects unauthenticated requests away from `/library` and `/feed`. Every route handler that touches story data (`api/stories/*`, `api/feed/*`, and `api/generate` whenever a `storyId` is present) independently re-checks `auth()` and re-verifies row ownership, rather than trusting the proxy layer alone — this follows Next.js's own documented guidance that middleware/proxy should not be relied on as the sole authorization boundary for data access.

## Consequences

- Guest use of the core write flow (`/`, `/story` without a `storyId`) is entirely unaffected — no new required network call, no new failure mode, no behavior change. This was a hard constraint from the Writer and is structurally guaranteed by `ensureStoryId()` short-circuiting to `undefined` whenever there's no session.
- A Writer switching accounts or signing out mid-story does not retroactively unpersist anything already written under the prior session — `storyId` in client state simply stops being reusable once ownership no longer matches, and the next turn (if the Writer isn't signed back in) reverts to guest (unpersisted) behavior for the remainder of that session.
- JWT sessions mean revoking a specific session (as opposed to rotating `AUTH_SECRET`, which revokes all of them) isn't possible without additional plumbing (e.g. a server-side denylist) — an accepted tradeoff given the Credentials-provider constraint above; worth revisiting if a future requirement needs per-session revocation.
- The `stories`/`storyParagraphs` schema closely mirroring `StoryState`/`StoryParagraph` makes the persistence code in `/api/generate` and `/api/stories/[id]`'s `GET` (hydration) nearly mechanical translations rather than a second data model to keep in sync by hand — but it also means a future client-side shape change (e.g. a new per-paragraph field) will usually need a matching migration, not just a client-side change.
- No migration tooling decision is recorded as final here since it wasn't exercised end-to-end against a live database during this pass (no `DATABASE_URL` was available in the build/dev environment) — `drizzle-kit generate`/`migrate` is the intended path per the original plan, but should be verified for real once the Writer provisions a Neon project.
